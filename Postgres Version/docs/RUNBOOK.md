# Postgres Version — Project Runbook

This is the command reference and operating guide for the local Airbnb analytics stack.

## What runs here

| Component | Where | Port |
| --- | --- | --- |
| PostgreSQL 17 | Docker container `airbnb-postgres` | host `5433` |
| pgAdmin 4 | Docker container `airbnb-pgadmin` | `5050` |
| dbt v1 | uv environment | CLI |
| Dagster | uv environment | `3001` |
| Metabase | Docker container `airbnb-metabase` | `3000` |

The local PostgreSQL 18 Windows service stays on port `5432` and is **not** used by this project. Docker Postgres is mapped to `5433` to avoid the conflict.

Python 3.13 is managed by `uv`; the project does not use the system Python 3.14.

## Prerequisites

```powershell
uv --version
docker --version
docker compose version
```

Docker Desktop must be running before the Docker commands. `uv` will download its own Python 3.13 on the first `uv sync`; you do not need to install 3.13 system-wide.

## First-time setup, in order

Run all commands from `Postgres Version/` unless a step says otherwise.

### 1. Enter the project root

```powershell
cd "Postgres Version"
```

This directory contains `compose.yaml`, `pyproject.toml`, and `uv.lock`.

### 2. Install the Python environment

```powershell
uv sync
```

What it does:

- reads `.python-version`;
- installs/uses a uv-managed Python 3.13;
- creates `.venv/`;
- installs the dbt and Dagster dependencies from `uv.lock`;
- installs the local Dagster package in editable mode.

It does **not** modify the system Python 3.14 installation.

### 3. Start Postgres, Metabase, and pgAdmin

```powershell
docker compose up -d
```

What it does:

- creates the `airbnb_postgres_data`, `airbnb_pgadmin_data`, and `airbnb_metabase_data` volumes;
- creates the `airbnb` and `metabase` databases;
- runs `docker/init/01_schema_roles.sql`, `02_raw_tables.sql`, `03_reporting.sql`, and `04_create_metabase_db.sql`;
- loads `data/raw/raw_listings.csv`, `raw_hosts.csv`, and `raw_reviews.csv` into the `raw` schema;
- starts pgAdmin on `http://localhost:5050`;
- starts Metabase on `http://localhost:3000`.

The init scripts run **only when the Postgres volume is empty**. They do not rerun on every start.

Check container status:

```powershell
docker compose ps
```

Expected: `airbnb-postgres` is `Up ... (healthy)`, `airbnb-metabase` is `Up ... (healthy)` after its first-start initialization, and `airbnb-pgadmin` is `Up`. Metabase can take 1–2 minutes to become healthy on the first start.

### 4. Verify the raw data

```powershell
docker compose exec postgres psql -U postgres -d airbnb -c "SELECT 'listings' AS table_name, count(*) FROM raw.raw_listings UNION ALL SELECT 'hosts', count(*) FROM raw.raw_hosts UNION ALL SELECT 'reviews', count(*) FROM raw.raw_reviews;"
```

Expected counts with the current CSVs:

| Table | Rows |
| --- | --- |
| `raw.raw_listings` | 17,499 |
| `raw.raw_hosts` | 14,111 |
| `raw.raw_reviews` | 410,284 |

### 5. Install dbt packages

```powershell
cd airbnb_dbt
uv run dbt deps --profiles-dir ..
```

`--profiles-dir ..` points dbt at `Postgres Version/profiles.yml`. `uv run` automatically uses the workspace `.venv`.

### 6. Check the dbt connection

```powershell
uv run dbt debug --profiles-dir ..
```

Expected: `All checks passed!` with host `localhost`, port `5433`, and database `airbnb`. The profile's default schema is `staging`; model schema routing is defined in `airbnb_dbt/dbt_project.yml` and `generate_schema_name`.

### 7. Build and test the dbt project

```powershell
uv run dbt build --profiles-dir ..
```

This runs the seeds, snapshots, models, and tests in dependency order. The project should finish with:

```text
Completed successfully
Done. PASS=126 WARN=0 ERROR=0 SKIP=0 NO-OP=5 REUSED=0 TOTAL=131
```

The five `NO-OP` nodes are the dashboard exposures (dbt reports exposures, not builds, in a `build` run). `uv run dbt test --profiles-dir ..` runs the 107 data tests and finishes with `PASS=107`.

Where the objects land:

- `raw` — CSV-loaded source tables.
- `staging` — ephemeral `src_*` models, `int_*` views, and seeds.
- `analytics` — `dim_*`, `fct_reviews`, and `mart_*` tables; this is what Metabase reads.
- `snapshots` — `scd_raw_hosts` and `scd_raw_listings`.

### 8. Start Dagster

```powershell
cd ../airbnb_dagster_project
uv run dagster dev -p 3001
```

Open `http://localhost:3001`.

Dagster loads `airbnb_dagster_project.definitions`, which contains the dbt assets and the `materialize_dbt_models_schedule` schedule. The dbt manifest is generated by `DbtProject.prepare_if_dev()`.

Leave this terminal open while using the Dagster UI. Press `Ctrl+C` in that terminal to stop Dagster.

> `dagster dev` prints a deprecation warning suggesting `dg dev`. The current project uses the legacy `@dbt_assets` layout, so `dagster dev` is the supported command here.

### 9. Open pgAdmin (optional)

Open `http://localhost:5050` and sign in:

| Field | Value |
| --- | --- |
| Email | `admin@example.com` |
| Password | `admin123` |

The `Airbnb Postgres` server is pre-registered. On first connection, enter the database password `cikalmerdeka`.

Servers → Airbnb Postgres → Databases → airbnb → Schemas

  ├── staging    → int_* views and seed_* tables (internal)
  ├── analytics  → dim_*, fct_reviews, mart_* (BI-facing)

Right-click a table → **View/Edit Data** → **First 100 Rows**. Use the refresh button after running dbt or Dagster.

### 10. Open Metabase

Metabase is part of the Compose stack, so `docker compose up -d` already
started it. Open `http://localhost:3000`.

On the first start, complete the setup wizard:

1. Create the Metabase admin account.
2. When asked to add a database, choose **PostgreSQL**.
3. Enter the connection values below.

| Field | Value |
| --- | --- |
| Display name | `Airbnb Analytics` |
| Host | `postgres` (the Compose service name) |
| Port | `5432` (inside the Docker network) |
| Database | `airbnb` |
| User | `metabase` |
| Password | `metabasePassword123` |
| SSL | Off |

Metabase stores its own application data in the separate `metabase` database
inside the same Postgres container. That database is created by
`docker/init/04_create_metabase_db.sql` on a fresh volume. On an existing
volume, create it once manually:

```powershell
docker compose exec postgres psql -U postgres -d airbnb -c "CREATE DATABASE metabase;"
```

Query the `analytics` schema, not `staging`. `analytics` contains `dim_*`,
`fct_reviews`, and `mart_*`; `staging` is internal and the `reporter` role has no
`USAGE` on it. The card-by-card build guide is in
[`METABASE_DASHBOARDS.md`](METABASE_DASHBOARDS.md), and the native-SQL versions
with Field Filter variables are in
[`METABASE_SQL_WITH_FILTERS.md`](METABASE_SQL_WITH_FILTERS.md).

Dagster uses `3001` and Metabase uses `3000`, so they can run at the same time.

### 11. Save and version the Metabase content

The `metabase/` folder holds two different artifacts:

| Artifact | Purpose | Size | Git |
| --- | --- | ---: | --- |
| `metabase/export/**/*.json` | Collections, questions/models, dashboards, SQL, visualization settings, filter mappings | 26.5 KB for 14 cards + 1 dashboard; under 1 MB for the full set | Commit |
| `metabase/backups/*.dump` | Exact `.dump` of the Metabase application database, including users and settings | ~1.1 MB per dump | **Do not commit** |

Export the definitions after adding or changing dashboards:

```powershell
uv run python scripts\export_metabase.py
```

The exporter reads `METABASE_URL` and `METABASE_API_KEY` from `.env` and walks
the `Airbnb Analytics` collection (`id=5`) and its subcollections. It is
read-only. The output is cleaned of timestamps, view counts, last-editor
identity, public-sharing tokens, and permission flags.

Back up the full application database before an upgrade or a reset:

```powershell
.\scripts\backup_metabase.ps1
```

Restore it (destructive; replaces the current Metabase app DB):

```powershell
.\scripts\restore_metabase.ps1 -DumpFile .\metabase\backups\metabase_20261106_133517.dump
```

The restore script stops Metabase, recreates the `metabase` database, runs
`pg_restore`, and waits for `/api/health`. The analytics `airbnb` database is
not touched.

What to commit:

```text
metabase/export/
scripts/export_metabase.py
scripts/backup_metabase.ps1
scripts/restore_metabase.ps1
metabase/README.md
metabase/.gitignore
```

Never commit:

```text
.env
metabase/backups/*.dump
```

`metabase/.gitignore` excludes the dumps. The full guide, including the API-key
setup and the Pro serialization alternative, is in
[`../metabase/README.md`](../metabase/README.md).

## How dbt and Dagster fit together

This is the most important distinction in the project:

- **dbt is the transformation layer.** It contains the SQL models, tests, seeds, snapshots, and the logic that creates the analytics tables in Postgres.
- **Dagster is the orchestration layer.** It does not transform data itself. It decides *when* and *how* to run dbt, invokes the dbt CLI, shows the dbt models as assets, records run history, and lets you schedule or re-run the pipeline.

In other words:

```text
Dagster: "Run the pipeline now / at midnight / retry the failed asset."
   │
   ▼
dbt CLI: "I will build the seed, snapshots, models, and tests in dependency order."
   │
   ▼
Postgres: "I store the raw data and the resulting analytics tables."
```

### dbt's role

dbt owns everything that happens **inside** the transformation:

- reads the raw tables from `raw.raw_listings`, `raw.raw_hosts`, and `raw.raw_reviews`;
- compiles and runs the SQL models in `airbnb_dbt/models/`;
- applies materializations (`view`, `table`, `incremental`, `ephemeral`);
- runs the seeds `seed_full_moon_dates` and `seed_review_topics`;
- manages the snapshots `scd_raw_hosts` and `scd_raw_listings`;
- runs the data tests defined in `schema.yml`, `sources.yml`, and `tests/`;
- writes intermediate views and seeds into `staging`, dimensions/fact/marts into `analytics`, and snapshots into `snapshots`;
- generates `target/manifest.json`, which describes the model graph, columns, tests, and dependencies.

dbt is fully usable on its own:

```powershell
cd airbnb_dbt
uv run dbt build --profiles-dir ..
```

That command does the same transformation work whether or not Dagster is running. It does **not** create a Dagster run or show up in the Dagster UI.

### Dagster's role

Dagster owns everything **around** the transformation:

- loads the dbt project and reads `target/manifest.json`;
- exposes every dbt model, seed, and snapshot as a Dagster **asset**;
- exposes dbt tests as Dagster **asset checks**;
- builds the asset dependency graph from the dbt manifest;
- starts a run when you click **Materialize** in the UI;
- invokes `dbt build` through `DbtCliResource`;
- streams dbt logs into the Dagster run viewer;
- records success/failure, timing, materializations, and test/check results;
- supports schedules, manual runs, retries, and re-running selected assets;
- gives you a single place to see the pipeline's operational history;
- can later orchestrate non-dbt steps too (for example, loading a new CSV, refreshing Metabase, or calling an API).

Dagster **does not**:

- rewrite or replace your dbt SQL;
- write analytics rows directly to Postgres;
- replace the dbt model graph or dbt tests;
- load the raw CSVs (the Docker init scripts do that);
- run anything while `dagster dev` is stopped.

### Side-by-side comparison

| Question | dbt | Dagster |
| --- | --- | --- |
| Main responsibility | Transform data with SQL | Orchestrate and observe the pipeline |
| Writes data to Postgres? | Yes, through the models | No, it invokes dbt |
| Defines models and tests? | Yes | No, it imports the dbt manifest |
| Knows the model dependency order? | Yes, from `ref()` and `source()` | Yes, from the dbt manifest |
| Decides when to run? | No, you run the CLI | Yes, UI, schedule, or API |
| Run history? | dbt logs and artifacts | Dagster runs, events, asset history |
| Scheduling and retries? | Limited | Yes |
| UI? | dbt docs | Dagster UI |
| In this project | `airbnb_dbt/` | `airbnb_dagster_project/` |

### dbt CLI vs Dagster materialization

| Capability | dbt CLI | Dagster |
| --- | --- | --- |
| Run everything | `dbt build` | **Materialize all** |
| Run a specific model | `dbt run --select dim_listings` | Select the asset → **Materialize selected** |
| Run tests | `dbt test` (or included in `dbt build`) | dbt tests appear as **asset checks** |
| Schedule | External cron/script | Built-in schedule |
| Retries/backfills | Manual | UI/API driven |
| Run history and logs | dbt logs/artifacts | Dagster run history + per-asset logs |
| dbt model graph | dbt DAG | Imported into the Dagster asset graph |
| Non-dbt tasks | Not its job | Can orchestrate Python/SQL/other steps later |

Examples from `airbnb_dbt/`:

```powershell
# Build everything (seed + snapshots + models + tests)
uv run dbt build --profiles-dir ..

# Run only one model
uv run dbt run --select dim_listings --profiles-dir ..

# Run one model and its upstream parents
uv run dbt build --select +fct_reviews --profiles-dir ..

# Run tests only
uv run dbt test --profiles-dir ..
```

Important nuances:

- **Direct dbt CLI runs do not appear in Dagster.** If you run `dbt build` yourself, Dagster has no run history for it. If you materialize through Dagster, the run, logs, asset materializations, and test results are recorded.
- **Dagster does not replace dbt.** It reads `target/manifest.json` to understand the dbt graph and then invokes the dbt executable.
- **`dbt build` vs `dbt run`:** `dbt build` also runs seeds, snapshots, and tests; `dbt run` only runs models. The Dagster asset uses `dbt build`.
- **Not every dbt node is a separate Dagster asset.** The ephemeral `src_*` staging models are compiled into downstream SQL, so they do not appear as standalone materialized assets. Seeds, snapshots, and materialized models do.
- **The schedule is stopped by default.** Start `materialize_dbt_models_schedule` in the Dagster UI if you want the daily midnight run. It only fires while the Dagster daemon is running.
- **Run history is temporary under `dagster dev`** unless you set a persistent `DAGSTER_HOME`.

### The Dagster files in this project

| File | What it does |
| --- | --- |
| `airbnb_dagster_project/airbnb_dagster_project/definitions.py` | Registers the dbt assets, the dbt resource, and the schedule in a `Definitions` object. |
| `.../assets.py` | Defines `airbnb_dbt_dbt_assets` with `@dbt_assets`. When Dagster materializes it, the function runs `dbt.cli(["build"]).stream()`. |
| `.../project.py` | Creates the `DbtProject`, points it at `airbnb_dbt/` and `Postgres Version/profiles.yml`, and calls `prepare_if_dev()` to generate/refresh the dbt manifest. |
| `.../schedules.py` | Creates `materialize_dbt_models_schedule`, a daily `0 0 * * *` schedule that runs the `dbt_select="fqn:*"` selection (the whole dbt project). |
| `airbnb_dagster_project/pyproject.toml` | Declares `dagster`, `dagster-dbt`, and `dagster-webserver`, and sets `[tool.dagster] module_name`. |

The relevant code is intentionally small. The dbt project does the heavy transformation work; Dagster wraps it.

### What happens when you click “Materialize” in Dagster

1. You open `http://localhost:3001` and select one or more assets, or click **Materialize all**.
2. Dagster creates a run and resolves the selected asset graph.
3. The `@dbt_assets` function is called with a `DbtCliResource`.
4. Dagster starts the dbt CLI with the corresponding dbt selection (for example, the whole project or only the selected models).
5. dbt connects to Postgres at `localhost:5433` using `profiles.yml`.
6. dbt runs the seed, snapshots, models, and tests in dependency order.
7. Dagster streams the dbt logs into the run viewer.
8. Each dbt model materialization is recorded against the matching Dagster asset.
9. Each dbt test result is recorded as a Dagster asset check.
10. You can refresh pgAdmin or the row-count watcher to see the resulting database changes.

If a model or test fails, Dagster records the failure on the corresponding asset/check, and the run history shows exactly where it stopped.

### The schedule

`schedules.py` defines a daily schedule at midnight:

```python
build_schedule_from_dbt_selection(
    [airbnb_dbt_dbt_assets],
    job_name="materialize_dbt_models",
    cron_schedule="0 0 * * *",
    dbt_select="fqn:*",
)
```

Important details:

- The schedule runs the **entire dbt project** (`fqn:*`).
- The schedule is created in a **stopped** state by default. Open Dagster → **Overview** → **Schedules**, find `materialize_dbt_models_schedule`, and start it if you want automatic daily runs.
- The schedule only fires while the Dagster daemon is running. `dagster dev` runs the webserver and daemon together for local development.
- The cron expression `0 0 * * *` means “every day at 00:00” in the Dagster instance's timezone.
- If you only want to transform data once, you do not need the schedule; run `dbt build` or materialize the assets manually.

### Run history and Dagster storage

`dagster dev` uses a temporary Dagster home directory by default:

```text
airbnb_dagster_project/.tmp_dagster_home_*
```

This means run history and asset materialization history are for the current dev session. If you want the history to survive restarts, set a persistent `DAGSTER_HOME` directory before starting Dagster. The analytics data itself is unaffected; it always lives in Postgres.

For production, Dagster normally runs `dagster-webserver` and `dagster-daemon` separately with a persistent `DAGSTER_HOME` and a real run/event storage backend.

### Do you need Dagster to use dbt?

No. The minimum workflow is:

```powershell
cd airbnb_dbt
uv run dbt build --profiles-dir ..
```

Use Dagster when you want:

- a visual asset graph and run history;
- a schedule or manual trigger;
- logs and failure tracking in one place;
- the ability to re-run only selected models;
- dbt tests shown as asset checks;
- a foundation for orchestrating non-dbt tasks later.

## How to reset Postgres and start fresh

Use this when you want an empty database. The first part deletes the Postgres data; the second part starts Dagster and materializes the assets one by one.

### 1. Stop Dagster

Stop the `uv run dagster dev -p 3001` process with `Ctrl+C` in its terminal. If you cannot find that terminal, stop the process listening on port 3001:

```powershell
Get-NetTCPConnection -LocalPort 3001 -State Listen -ErrorAction SilentlyContinue |
  Select-Object -ExpandProperty OwningProcess |
  ForEach-Object { Stop-Process -Id $_ -Force }
```

### 2. Delete the Postgres data and start fresh

From `Postgres Version/`:

```powershell
docker compose down -v
docker compose up -d
```

What `down -v` deletes:

- the `airbnb_postgres_data` volume (all databases, schemas, and tables, including the Metabase application database);
- the `airbnb_pgadmin_data` volume (pgAdmin settings and saved connections);
- the `airbnb_metabase_data` volume (Metabase uploads and plugins).

What it does **not** delete:

- `data/raw/*.csv` — the source CSVs stay on disk;
- `airbnb_dbt/` and `airbnb_dagster_project/` — all project files stay.

The next `up` recreates both databases and re-runs `docker/init/`, so the raw
tables are loaded again and Metabase starts with an empty application database.
You will need to re-run the Metabase setup wizard and recreate saved questions
and dashboards. `down -v` is the supported full reset. Dropping only the
`airbnb` database keeps Metabase but requires re-running the init scripts and a
full `dbt build` manually.

Verify the fresh raw data:

```powershell
docker compose ps
docker compose exec postgres psql -U postgres -d airbnb -c "SELECT 'listings' AS table_name, count(*) FROM raw.raw_listings UNION ALL SELECT 'hosts', count(*) FROM raw.raw_hosts UNION ALL SELECT 'reviews', count(*) FROM raw.raw_reviews;"
```

### 3. Reset only Postgres and keep pgAdmin settings

If you want to delete the database without losing pgAdmin configuration:

```powershell
docker compose stop postgres
docker compose rm -sf postgres
docker volume rm airbnb_postgres_data
docker compose up -d postgres
```

This removes only the Postgres volume. The init scripts run again and reload `data/raw/`.

## Fresh restart: step-by-step materialization

After the reset above, start Dagster and materialize the assets one at a time.

### 1. Start Dagster

```powershell
cd airbnb_dagster_project
uv run dagster dev -p 3001
```

## Troubleshooting

### Dagster is not reachable on port 3001

Dagster is a foreground dev server; it is only available while `uv run dagster dev -p 3001` is running. Start it from `airbnb_dagster_project/`.

Check for a port conflict:

```powershell
Get-NetTCPConnection -LocalPort 3001 -State Listen
```

If another process owns the port, stop it or use another port, e.g. `-p 3002`.

### pgAdmin is not reachable on port 5050

pgAdmin can take up to a minute to initialize. Check:

```powershell
docker compose ps
docker compose logs pgadmin --tail 50
```

If the pgAdmin login is rejected, verify the email/password in `.env` and restart the container. If the volume contains old configuration, reset it with:

```powershell
docker compose rm -sf pgadmin
docker volume rm airbnb_pgadmin_data
docker compose up -d pgadmin
```

This removes only pgAdmin settings, not the Postgres data.

### dbt cannot connect to Postgres

1. Confirm Postgres is healthy: `docker compose ps`.
2. Confirm port `5433` is mapped: `docker compose port postgres 5432`.
3. Confirm `profiles.yml` uses `localhost:5433` and the same password as `.env`.
4. Re-run `uv run dbt debug --profiles-dir ..`.

### The raw tables are empty or missing

The init scripts only run on an empty volume. Confirm the CSVs exist in `data/raw/`, then reset:

```powershell
docker compose down -v
docker compose up -d
```

### Metabase is not reachable on port 3000

Metabase can take 1–2 minutes to initialize on its first start. Check:

```powershell
docker compose ps
docker compose logs metabase --tail 50
```

If the container is restarting, the most likely cause is that the `metabase`
application database does not exist yet (it is only created on a fresh
Postgres volume). Create it and restart:

```powershell
docker compose exec postgres psql -U postgres -d airbnb -c "CREATE DATABASE metabase;"
docker compose restart metabase
```

If port `3000` is already used by another process, change `METABASE_PORT` in
`.env` and run `docker compose up -d metabase`.

### Metabase cannot see the `analytics` tables

First confirm the database connection uses host `postgres` and port `5432`
(inside Docker), not `localhost:5433`. Then check the grants.

The reporting grants are applied by `docker/init/03_reporting.sql` on a fresh volume. On an existing database, run them once manually from `Postgres Version/`:

```powershell
Get-Content -Raw .\docker\init\03_reporting.sql | docker compose exec -T postgres psql -U postgres -d airbnb
```

Verify the `metabase` user can read `analytics` but not `staging`:

```powershell
docker compose exec -T -e PGPASSWORD=metabasePassword123 postgres psql -U metabase -d airbnb -c "select count(*) from analytics.dim_listings;"
docker compose exec -T -e PGPASSWORD=metabasePassword123 postgres psql -U metabase -d airbnb -c "select count(*) from staging.int_listings_enriched;"
```

### `seed_full_moon_dates.csv` or `seed_review_topics.csv` is missing after a fresh clone

Both seed files are tracked in `airbnb_dbt/seeds/`. The root `.gitignore` ignores `*.csv` but explicitly unignores these two seeds. If you copy the repo manually, make sure both files are included.

### Python 3.14 is being used instead of 3.13

Run:

```powershell
uv python find 3.13
uv run python --version
```

The project's `.venv/pyvenv.cfg` should show `home = ...uv\python\cpython-3.13...`. If not, delete `.venv/` and run `uv sync` again.

### dbt package resolution or deprecation warnings

```powershell
cd airbnb_dbt
uv run dbt deps --profiles-dir ..
```

Current packages: `dbt_utils` 1.4.1, `metaplane/dbt_expectations` 0.10.10, `godatadriven/dbt_date` 0.21.0.

### dbt v2 / Fusion

dbt v2 is GA, but it does **not** support Postgres yet. This project intentionally uses dbt v1 (`dbt-core` 1.12 + `dbt-postgres` 1.11). When the Postgres adapter becomes available, the migration is:

```powershell
# future migration only — not currently supported with Postgres
uv remove dbt-core dbt-postgres
uv add "dagster-dbt[dbt]"
```
